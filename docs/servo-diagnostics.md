# 舵机串口诊断与固件恢复

机械臂左侧Type-C口的CP2102N以115200/8N1连接ESP32；ESP32内部以GPIO18 RX、GPIO19 TX、1Mbps连接舵机总线。USB发送原厂JSON，不能直接向该USB口发送ST3215二进制协议。原厂Python串口例程只是发送JSON加换行，控制链路与本项目SerialTransport一致。

原厂T101按关节控制：1底座ID11，2肩主动12与从动13联动，3肘ID14，4夹爪ID15。rad是绝对角度；spd单位steps/s，4096steps/圈，spd0为最大速度，现场诊断应显式低速。不要根据失败读取后留下的默认或缓存位置计算相对运动。T105不查询ID13，T1051和软件connected=true本身也不能证明舵机在线。

诊断时先排除竞争控制者，保存实际发送与原始串口回复，并配合现场观察。原厂固件没有通用任意ID扫描/小步接口。不要用改ID、校准、PID修改冒充读取，也不要用解锁力矩作通信测试：负载机械臂解锁可能下坠。项目服务停止时会执行自己的停车逻辑，可能额外发出T123和T102；单独串口测试应记录这些命令。

临时诊断固件位于本机`agent/codex/control-loss-20261009/servo-diag`，运行前必须完成备份检查。它只提供显式ID的扫描、实时读取和小步，完整肩12/13应同步反向动作。孤立安装的Arduino core启动代码已移除NVS初始化/自动擦除及OTA标记操作，避免诊断固件修改原厂配置；原bootloader行为仍由真实OTA状态决定。

## 临时刷写的前提

1. 用ROM下载模式识别实际芯片、物理Flash容量、Flash加密与Secure Boot状态；不修改eFuse、不使用force或encrypt绕过限制。
2. 读取整个物理Flash两次，比对一致，再用verify_flash校验与设备一致。备份保留在开发机和RK3588两处；完整备份包含bootloader、分区表、OTA选择、两个应用区、NVS和文件系统。
3. 从备份验证真实分区表MD5，解析OTA选择及应用镜像校验。活动应用NEW/PENDING_VERIFY或选择不明确时停止，不猜测刷写地址。诊断镜像必须完全落在活动应用分区内。
4. 只写诊断app，不刷构建产物中的bootloader、partition或boot_app0，不清空Flash。写入后校验app，并确认活动应用分区以外保持原始内容。

每次Flash事务须持有同一个flock直到恢复及校验完成，并等待上一进程实际退出；不允许前一次恢复尚未结束就开始下一次连接。进入ROM用default_reset，已经确认处于ROM才用no_reset。应用启动应显式释放DTR（GPIO0高）再切换RTS复位，并等待真实启动应答；esptool的hard_reset只切RTS，no_reset会话可能留下DTR状态，不能单凭“Hard resetting”日志判定应用已运行。

2026-10-09实测设备ESP32-D0WD-V3 rev3.1、4MiB Flash、未启用Flash加密/Secure Boot。备份解析活动app0偏移0x10000、大小0x140000；这些值只属于当前设备，不能用作其他设备的默认值。离线镜像校验只能证明备份可用，不能称为已经实体恢复。

## 恢复原厂固件

保持ROM下载状态，使用备份的活动应用**整分区**切片恢复并校验。若其他持久化区域有变化，使用完整Flash备份恢复。esptool参数使用`--flash_mode keep --flash_freq keep --flash_size keep`，避免改动原镜像头。全Flash备份从地址0写回，不涉及eFuse。

恢复校验完成后才重启原厂应用、恢复正常串口服务，并检查原厂Wi-Fi网页/JSON响应。原厂固件启动可能执行初始化动作，应保持机械臂活动空间畅通。固件恢复不等于舵机故障已经修复；必须分别记录固件恢复与舵机通信/运动结果。

实际备份、命令、SHA和现场结果保存在`agent/codex/control-loss-20261009`；执行报告在`agent/report`，不随公开仓库分发备份。

## 持续诊断的当前运行方式

原厂完整Flash已实际写回并整图校验一致，原厂网页与JSON恢复得到验证。用户随后授权持续保留诊断固件，因此当前ESP32运行诊断应用，原厂Wi-Fi网页和OLED更新不可用；RK的`roarm-camera.service`保持停止，不能用生产服务向诊断固件发送原厂JSON。恢复能力已验证，舵机故障仍未修复。

所有串口测试与刷写共用RK路径`/opt/roarm-camera/agent/codex/control-loss-20261009/flash-transaction.lock`。`install_diagnostic.sh`只部署指定SHA的应用并等待真实ready，不自动恢复原厂；旧`temporary_diagnosis.sh`包含自动恢复逻辑，不适用于当前持续诊断。不能在上一硬件进程未退出时启动下一次测试。

| 诊断指令 | 用途及结果边界 |
| --- | --- |
| T7000 | Ping扫描ID 0–253，报告实际应答ID。 |
| T7001 | 指定ID实时读取；通信失败返回null，不能当作位置。 |
| T7002 | 指定ID相对小步，必须先有新鲜、无故障、位置模式且力矩开启的实测；单颗最大±5°。 |
| T7003 | 两个明确ID一次同步小步，各最大±2°，任一实读失败均不写；肩12/13须配对反向。 |
| T7004 | 原始只读Ping；支持8档主机UART波特率，记录RX字节、短写、错误及GPIO18空闲电平；不改舵机波特率寄存器。 |
| T7005 | UART1内部回环自检，发送合法Ping后关闭回环，再报告是否逐字节一致；仅验证内部UART，不证明外部线路或舵机正常。 |

T7004全扫没有收到字节，与JSON RPC超时是不同结果。回显也不能当作舵机应答。当前所有实读失败，尚未执行T7002/T7003，不能报告电机运动成功或据此判定电机烧毁。

## 定位外部总线

[厂家底板原理图](https://files.waveshare.com/wiki/RoArm-M2-S/General_Driver_for_Robots.pdf)的发送路径为GPIO19→U4→DATA，接收路径为DATA→U5→GPIO18；Q3与TXEN控制半双工收发方向，不依赖额外方向GPIO。DATA有3.3V上拉，发送期间接收缓冲关闭，因此未收到自己的发送回显属于正常现象。

UART内部自检通过而外部RX为0时，仍需区分GPIO输出、底板收发电路、接头和舵机通信电路。万用表只能检查空闲电压；定位收发路径需要观察GPIO19、DATA和GPIO18波形，或使用独立舵机测试板交叉测试。UART写入成功、GPIO18空闲高电平以及舵机端12V，都不能单独证明DATA信号已送到舵机。
